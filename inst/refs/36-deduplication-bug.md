# Deduplication bug: stacked pseudopeople threshold collapse

## Summary

The headline failure in the stacked pseudopeople dedupe benchmark was not just
"the model likes too many edges." The main bug was in evaluation: `il_accuracy()`
and `il_confusion_matrix()` were letting **blocking misses** count as thresholded
positives, even though `predict()` can never emit pairs that were not generated by
blocking.

That bug forced the selected threshold toward zero, which then made the benchmark
run `predict()` on essentially the whole blocked candidate graph and produced the
14.4M-pair / 733k-cluster pathology reported in `inst/benchmarks/pseudopeople.typ`.

## What was wrong

### 1. Blocking misses were treated as thresholdable predictions

`score_labeled_pairs()` scores every labelled pair directly from the source data.
That is fine for diagnostics, but `compute_confusion_counts()` was then using
`label_probs >= threshold` without also requiring `found_by_blocking`.

Effect:

- blocked-miss true pairs could still count as TPs in `il_accuracy()`
- recall was overstated
- the "best" threshold drifted toward `0`
- the benchmark then fed that near-zero threshold into `predict()` and
  `il_cluster()`, causing massive over-linking

In the stacked pseudopeople case, the sampled labelled-pair analysis showed that
almost all true duplicate pairs were blocking misses, so this bug completely
distorted threshold selection.

### 2. EM stored the blocking-adjusted prior as the global prior

While investigating, a second bug showed up in `il_estimate_em()`: the prior used
inside a blocked EM session was being written back to the model as though it were
the global prior. On `fake_1000` this inflated the stored prior from about
`0.0009` to `0.31`.

That did not explain the stacked pseudopeople threshold collapse by itself, but it
was still a real correctness bug and is now fixed.

### 3. `cl_null()` levels were being collapsed into gamma 0

The R and SQL gamma paths were treating null-handling levels as ordinary
disagreement (`gamma = 0`) rather than as Splink-style null states (`gamma = -1`)
that contribute zero weight and are excluded from m/u estimation.

This also did not fully explain the stacked benchmark on its own, but it was a
real parity/correctness bug and is now fixed.

## Code changes made

### Blocking-aware evaluation

- `R/utils-evaluation.R`
  - `compute_confusion_counts()` now gates `predicted_positive` by
    `found_by_blocking`
  - `NA` blocking flags are treated as not found
  - `fn_blocking_miss` is now the count of actual positives that were never
    generated by blocking

### EM prior fix

- `R/utils-scoring.R`
  - added helpers to clamp probabilities and convert between probability and
    Bayes-factor odds
  - added helpers to apply and reverse blocking adjustments to the prior
- `R/il_estimate_em.R`
  - EM still trains on the blocking-adjusted prior internally
  - the model now stores the **reversed global prior** after training
  - the `fix_prior` docs were corrected to match the actual default (`FALSE`)

### Null gamma fix

- `R/utils-em.R`
  - `cl_levels(cl_null(), ...)` now emits `gamma = -1` for null matches
  - EM and derived-prior code now skip negative gammas
- `R/utils-scoring.R`
  - match-weight scoring now gives null gammas zero contribution
- `R/utils-sql.R`
  - SQL gamma generation for `cl_levels()` now emits `-1` for null states

### Tests added

- `tests/testthat/test-em-prior.R`
- `tests/testthat/test-null-gamma.R`
- `tests/testthat/test-evaluation-blocking.R`

## What the stacked benchmark means after the fix

After the evaluation fix, the stacked benchmark no longer chooses an "all pairs"
threshold. The best threshold moved from effectively `0` to about `0.99`/`1.0`
in reruns, and emitted pairs dropped sharply (one full rerun produced about
3.0M predicted pairs instead of 14.4M).

The important interpretation change is:

- **before**: the benchmark looked like a pure over-linking failure
- **after**: the benchmark is exposed as a **blocking-recall failure first**
  and a scoring/clustering issue second

That is a much more honest diagnosis of the stacked dedupe scenario.

## Remaining note

The stacked pseudopeople benchmark still performs poorly on pairwise duplicate
detection after the fixes above. The difference is that the package now reports
that failure honestly instead of selecting a zero threshold that turns the whole
candidate graph into predicted duplicates.
