# 25 — Phonetics on SQLite: Investigation and Outcome

> Investigates whether `il_soundex` can be made available as a SQL
> function on SQLite, closing the gap identified in the gap audit that
> preceded ref 24.

---

## Context

The gap audit (preceding `24-two-fixes.md`) identified that phonetic
blocking with `il_soundex` works on DuckDB (via a registered MACRO) and
PostgreSQL (via the native `soundex()` function), but fails on SQLite
with a hard error from `validate_phonetic_dialect()`.

Phonetic *comparisons* on SQLite work correctly — the R-side gamma path
in `utils-em.R` applies `comp$transform(val)` directly to the R vectors
before computing gamma, so `il_soundex` runs in R and the result is
passed to `compute_gamma()`.  The gap is only in **blocking rules**,
where the transform must be embedded in a SQL `WHERE` clause.

The proposed fix was to register `il_soundex` as a SQLite scalar UDF
via RSQLite, analogously to how DuckDB registers it as a MACRO.

---

## What Splink Does

An inspection of the splink Python source confirmed the original
hypothesis: **splink does not compute phonetics in SQL at all**.

- `phonetic_transform()` and `phonetic_transform_df()` are Python-only
  functions using the `phonetics` PyPI library (pandas `.apply()`).
- `NameComparison(col, dmeta_col_name='surname_dm')` expects the user
  to have pre-computed a dmetaphone column upstream in pandas before
  loading data.
- The actual SQL generated by `ArrayIntersectLevel` is
  `array_length(list_intersect(col_l, col_r)) >= 1` — an array set
  intersection on pre-materialised columns, not an on-the-fly phonetic
  computation.
- On SQLite, `@unsupported_splink_dialects(["sqlite"])` is applied to
  `ArrayIntersectLevel` — phonetics are entirely unsupported.

irelink's approach of computing phonetics on-the-fly inside SQL (via
DuckDB macros and PostgreSQL native functions) is therefore **already
superior to splink** on those backends.

---

## RSQLite Scalar UDF Investigation

RSQLite 2.4.6 does not expose `createFunction()` or any equivalent API
for registering R functions as SQLite scalar UDFs.  The full namespace
was inspected and confirmed to contain no such function.

SQLite's built-in `SOUNDEX()` (available in some builds) was also
tested.  On the RSQLite 2.4.6 / Windows 11 environment, calling
`SELECT SOUNDEX('Smith')` causes a **segmentation fault** — the
function is either not compiled into the bundled SQLite or the binding
is broken in this version.  Either way it cannot be relied on.

**Conclusion:** There is no clean path to SQL-side phonetic computation
on SQLite using the current RSQLite package.  Attempting to use
`il_soundex` in a blocking rule on SQLite correctly aborts with an
informative error, which is the right behaviour.

## Changes Made

### Documentation update (`R/il_phonetic.R`)

The SQL availability table and `@details` section were updated to
accurately describe the SQLite situation:

| Function        | DuckDB        | PostgreSQL      | SQLite                    |
|-----------------|---------------|-----------------|---------------------------|
| `il_soundex`    | ✓ (macro)     | ✓ (native)      | comparisons only (R-side) |
| `il_metaphone`  | ✗             | ✓ (native)      | ✗                         |
| `il_dmetaphone` | ✗             | ✓ (native)      | ✗                         |

A note was added explaining that phonetic transforms work in
comparisons on SQLite (via the R-side gamma path) but cannot be used
in blocking rules because SQLite does not support registering R scalar
UDFs.

No behaviour changed.  No new tests were added.

## Future Options

If SQLite phonetic blocking becomes important, the realistic paths are:

1. **Upgrade RSQLite**: A future version may expose scalar UDF
   registration (the underlying SQLite C API does support this via
   `sqlite3_create_function()`).  When that happens, a one-line change
   to `register_phonetic_macros()` would close the gap.

2. **Pre-materialise on SQLite**: Users on SQLite who need phonetic
   blocking can compute the phonetic column in R and write it to the
   database before calling `il_model()`:
   ```r
   df$surname_sx <- il_soundex(df$surname)
   model <- il_model(df, spec = ..., con = sqlite_con)
   # block on pre-computed column
   il_block_on(surname_sx)
   ```
   This matches splink's recommended approach for all backends.

3. **DuckDB for phonetics**: DuckDB is the recommended backend.
   SQLite is retained as a lightweight fallback without the full
   phonetic capability, which is an acceptable trade-off given that
   DuckDB is available on all platforms and is free.
